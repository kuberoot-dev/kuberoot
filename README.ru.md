# kuberoot

[English version](README.md)

kuberoot собирает дистрибутивы Kubernetes, которые загружаются прямо на железо. Каждый из них — один образ со своим ядром Linux, маленьким init, который поднимает Kubernetes, и нодой, которой управляют через сам API Kubernetes: нет SSH, нет оболочки и нет отдельной утилиты для ноды, до неё дотягивается `kubectl`. Всё поверх базы — пакеты [kubepkg](https://github.com/kuberoot-dev/kubepkg), так что дистрибутив — это база плюс метапакет, как дистрибутив Linux — это ядро плюс пакеты.

В репозитории собираются восемь дистрибутивов: `edge` — кластер общего назначения на одну или несколько нод; `router` — Kubernetes без контейнеров, работающий сетевым маршрутизатором; `hypervisor` — виртуальные машины на KVM с дисками, реплицируемыми между нодами, которые переезжают с отказавшей ноды; `ai` — языковые модели, которые работают процессами нод за одной точкой, совместимой с OpenAI, а новые версии кластер выкатывает и откатывает сам; `rt` — контроллер реального времени, поды которого получают целые процессоры без таймерного тика на полностью вытесняемом ядре; `iot` — шлюз без контейнеров, который читает устройства по Modbus и передаёт дальше то, что они сообщают, а изменения, отрезавшие устройство, откатываются сами; `observability` — кластер мониторинга снаружи того, за чем он следит: он сам читает BMC серверов, коммутаторы, PDU и пробы сервисов и своими heartbeat'ами сообщает внешнему миру, что всё ещё работает; и `workstation` — рабочие столы людей как виртуальные машины кластера, которые открываются из браузера или RDP-клиентом.

> Статус: эксперимент. Дистрибутив `edge` проходит набор тестов на соответствие Kubernetes (462 из 462 на кластере из трёх нод, Kubernetes 1.37.1), но API ноды и раскладка её состояния ещё могут меняться.

## Из чего состоит нода

- **Ядро**: Linux 6.18, собранное под дистрибутив, все драйверы встроены. Нода загружает только модули, которые назвал её профиль (DRBD для реплицируемого хранилища), подписанные ключом сборки; после них загрузка модулей выключается.
- **kinit**: PID 1. Монтирует корень только для чтения и раздел состояния, поднимает сеть, выпускает сертификаты ноды и запускает службы её роли: containerd, kubelet и kube-proxy на всех нодах, а на control plane ещё kine (хранилище кластера на SQLite), API-сервер, controller manager и планировщик.
- **API ноды**: каждая нода обслуживает `node.kuberoot.dev`, подключённый к API кластера, поэтому `kubectl get disks`, `kubectl get bootentries` или `kubectl create upgrade` действуют на ноду. Он работает и до того, как появится кластер, — так ноду и устанавливают.
- **Сеть подов**: VXLAN между нодами, или обычные маршруты в плоской сети, или никакой — для CNI-пакета вроде Cilium.
- **Пакеты**: оператор kubepkg работает на control plane и ставит пакеты дистрибутива; метапакет `edge` и пакеты платформы лежат в [kubepkg-recipes](https://github.com/kuberoot-dev/kubepkg-recipes).

## Дистрибутив router

`router` оставляет от Kubernetes только то, что хранит конфигурацию и следит за ней: kine, API-сервер, controller manager для сборки мусора и API ноды. Нет kubelet, среды запуска контейнеров, kube-proxy и планировщика. Конфигурация маршрутизатора — ресурсы `router.kuberoot.dev`, с RBAC, аудитом, watch и GitOps, как у любых ресурсов, а `kuberoot-router` приводит к ним ноду:

| Ресурс | Что настраивает |
|---|---|
| `Interface` | адреса и MTU линка или VLAN на родительском линке |
| `Route` | статический маршрут |
| `NATRule` | маскарадинг за исходящим линком или проброс порта на хост |
| `FirewallZone`, `FirewallRule` | зоны линков: что может достучаться до маршрутизатора и что может ходить между зонами |
| `DHCPServer` | DHCP на линке и DNS-кэш для него |
| `BGPRouter`, `BGPPeer` | AS маршрутизатора, анонсируемые сети и BGP-сессии |
| `Safeguard` | изменения на испытательном сроке, которые откатываются без подтверждения |

Домашний шлюз с LAN на `eth1` за внешним `eth0`:

```yaml
apiVersion: router.kuberoot.dev/v1alpha1
kind: Interface
metadata: {name: lan}
spec: {link: eth1, addresses: [192.168.10.1/24]}
---
apiVersion: router.kuberoot.dev/v1alpha1
kind: NATRule
metadata: {name: out}
spec: {masquerade: {outLink: eth0, sources: [192.168.10.0/24]}}
---
apiVersion: router.kuberoot.dev/v1alpha1
kind: DHCPServer
metadata: {name: lan}
spec: {link: eth1, rangeStart: 192.168.10.100, rangeEnd: 192.168.10.199}
---
apiVersion: router.kuberoot.dev/v1alpha1
kind: FirewallZone
metadata: {name: wan}
spec: {links: [eth0], input: Drop, management: true}
---
apiVersion: router.kuberoot.dev/v1alpha1
kind: FirewallZone
metadata: {name: lan}
spec: {links: [eth1], input: Accept, forwardTo: [wan]}
```

Каждый ресурс пишет в статус, исполняет ли его нода, а если нет — почему; интерфейсы показывают своё состояние, DHCP-серверы — аренды, BGP-соседи — сессии. Файрвол фильтрует только когда есть хотя бы одна зона, а API маршрутизатора остаётся открытым в зонах управления, что бы ни говорили правила. С `Safeguard` каждое изменение работает на испытательном сроке: если `spec.confirm` не назовёт его ревизию вовремя, маршрутизатор возвращается к последней подтверждённой конфигурации, так что изменение, отрезавшее администраторов, отменяет себя само.

## Дистрибутив hypervisor

`hypervisor` запускает виртуальные машины на KVM через cloud-hypervisor: без libvirt и без подов. Машина — ресурс кластера:

```yaml
apiVersion: vm.kuberoot.dev/v1alpha1
kind: VirtualMachine
metadata: {name: web}
spec:
  cpus: 2
  memory: 2Gi
  replicas: 3
  disk: {size: 20Gi, image: "https://example.org/images/debian-13-uefi.qcow2"}
```

`kuberoot-vmctl` на control plane кладёт диск машины на столько нод, сколько у неё реплик, а саму машину — на одну из них. Диск — том DRBD: каждая запись доходит до других нод прежде, чем считается сделанной, а нода, отрезанная от большинства, перестаёт писать. Когда нода машины лежит полминуты, машина запускается на другой ноде с её диском — с тем же диском и адресом; вернувшаяся нода догоняет остальные и убирает свою копию машины. Машины разных нод живут в одной сети (мост на каждой ноде, связанный VXLAN), а шлюз на control plane раздаёт адреса и выпускает наружу.

Работающая машина переезжает на другую ноду живой, когда её `spec.node` меняется на другую ноду с её репликой: на время переезда диск доступен на запись на обеих, память машины копируется, пока она работает, и машина продолжает работать там с тем же диском и адресом, без перезагрузки. Переезд, который не закончился за десять минут или потерял по дороге ноду, отменяется, и машина остаётся где была; `status.failedMigration` называет ноду, пока `spec.node` снова не изменится.

Каждая нода обслуживает свою часть через API ноды: `volumes` (диски на ней, с ролью и состоянием DRBD), `machines` (машины, которые она запускает) и `machines/console` (последовательная консоль машины). kubelet остаётся ради того, что кластер знает о нодах, — регистрации и пульса; подов нет.

## Дистрибутив ai

`ai` — кластер для инференса и обучения: это edge с подами и пакетами, плюс собственный способ обслуживать языковые модели без подов и без образов контейнеров. На каждой ноде llama-server, собранный в образ, работает отдельным процессом ноды. Модель — ресурс кластера:

```yaml
apiVersion: ai.kuberoot.dev/v1alpha1
kind: Model
metadata: {name: qwen}
spec:
  replicas: 3
  contextSize: 4096
  parallel: 2
  source:
    url: https://example.org/models/qwen2.5-0.5b-instruct-q4_k_m.gguf
    sha256: 74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db
```

`kuberoot-aictl` на control plane размещает модель на столько нод, сколько у неё реплик. Каждая нода скачивает веса, берёт их, только если они совпадают с хешем, и запускает сервер. Control plane отдаёт все модели через одну точку, совместимую с OpenAI, на порту 8000: `/v1/models`, `/v1/chat/completions` и остальные вызовы `/v1` уходят по имени модели из запроса к её готовым репликам по очереди, а потоковые ответы проходят насквозь по мере появления. Своей аутентификации у точки пока нет: она рассчитана на сеть, которой кластер доверяет.

Новый `spec.source` — новая версия. Сначала она ставится на одну ноду; когда там она готова и ответила на пробный запрос, остальные ноды берут её по одной, каждая — после того как предыдущая начала её обслуживать, так что из-за смены версии модель не теряет больше одной реплики. Версия, которая не запустилась на первой ноде, не стала там готова за пятнадцать минут или не ответила, откатывается: все ноды остаются на прежней версии, а `status.failedVersion` не даёт пробовать её снова, пока `spec.source` не изменится. `status.previous` — версия перед текущей; её веса остаются на нодах, и если вернуть её в `spec.source`, модель откатывается сразу.

Каждая нода обслуживает свою часть через API ноды: `modelservers` (модели, которые она обслуживает, их фаза и веса, на которых они работают) и `modelservers/log` (вывод сервера).

### GPU и пакеты

Дистрибутив ai — это edge с подами и пакетами. Поэтому всё остальное для работы с ИИ приходит пакетами kubepkg: дробление GPU, очереди, движки инференса, обучение, векторные базы и готовые их сочетания.

Драйвер NVIDIA — часть образа, а не контейнер, который его ставит. Открытые модули ядра собраны под ядро kuberoot и подписаны его ключом: других модулей оно не загружает. Библиотека CUDA-драйвера, NVML, nvidia-smi и прошивка GSP — из того же выпуска драйвера. Нода с GPU NVIDIA загружает драйвер при старте. kuberoot-node создаёт файлы устройств и описывает GPU для containerd как CDI-устройства (`nvidia.com/gpu=0`, `=all`), чтобы device plugin раздавал их подам, а OSConfig показывает их в `status.gpus`; kuberoot-aictl ставит таким нодам метку `nvidia.com/gpu.present=true`, по которой их находят GPU-пакеты, а CDI-хук NVIDIA в образе обновляет кэш загрузчика в контейнере под выданные ему библиотеки драйвера. Нода без GPU NVIDIA работает без драйвера. Модель тоже может работать на GPU: `spec.gpus` на реплику ставит её только на ноды, где столько GPU свободно, и запускает её со всеми слоями на GPU движком, который указан в её источнике: это llama-server, собранный под CUDA (от Turing до Hopper) и публикуемый рядом с каждым выпуском. Движок скачивается как веса — только нодами, которые его запускают, поэтому образ остаётся маленьким, а движок меняется без смены ОС; новый движок — это новая версия модели, и она выкатывается так же, как новые веса. GPU, отданные моделям, лучше не отдавать подам через device plugin.

### Агент-оператор

`kuberoot-agent` следит за кластером и спрашивает языковую модель, что делать с найденным: с нодами, которые не готовы, со службами нод, которые перезапускаются, с серверами моделей, которые падают, с моделями, которым не хватает реплик. Модель — одна из тех, что обслуживает кластер, или любая точка, совместимая с OpenAI. Сам агент ничего не делает. Он предлагает `Remedy` — одно из пяти действий: перезапустить службу ноды, перезапустить сервер модели на ноде, откатить модель на прежнюю версию, перезагрузить ноду или передать человеку, ничего не меняя. Модель выбирает только действие, и JSON-схема держит её в рамках действий, допустимых для этой проблемы. К чему действие применяется, берётся из самой проблемы, а не из ответа модели.

```yaml
apiVersion: ai.kuberoot.dev/v1alpha1
kind: Agent
metadata: {name: default}
spec:
  model: qwen
  autoApprove: []      # действия, которые выполняются без человека, например [RestartModelServer]
  maxPerHour: 4
```

Remedy выполняется, когда его одобрил человек (`kubectl patch remedy <имя> --type merge -p '{"spec":{"approved":true}}'`), или сразу, если его действие есть в `autoApprove` у Agent. Выполняет его `kuberoot-aictl`: по одному за проход и не больше `maxPerHour`. Кто бы ни одобрил, он отказывается перезагружать control plane и перезагружать ноду, пока лежит другая. У агента своя идентичность: его роль читает кластер и создаёт Remedy, а политика допуска не даёт ему одобрять, менять или удалять их. Remedy вместе с объяснением агента и тем, что он видел, — это запись всего, что он сделал и хотел сделать.
## Дистрибутив rt

`rt` — контроллер реального времени: цикл управления работает в поде и просыпается вовремя. Ядро полностью вытесняемое (PREEMPT_RT). Процессоры 0 и 1 держат собственную работу ноды, её прерывания и колбэки RCU; начиная со второго процессоры работают без таймерного тика, пока на них выполняется одна задача. Из них kubelet выдаёт целые процессоры подам класса Guaranteed, которые просят целые процессоры, с памятью из NUMA-узла этих процессоров, так что цикл получает свои процессоры в единоличное пользование:

```yaml
apiVersion: v1
kind: Pod
metadata: {name: loop}
spec:
  containers:
  - name: loop
    image: registry.example.org/plant/loop:1.4
    command: [chrt, --fifo, "80", /loop]
    securityContext:
      capabilities: {add: [SYS_NICE]}
    resources:
      requests: {cpu: "1", memory: 256Mi}
      limits: {cpu: "1", memory: 256Mi}
```

Задача с CAP_SYS_NICE работает с приоритетом реального времени (SCHED_FIFO); задачи реального времени могут занимать процессор целиком, а fair server ядра сохраняет рядом с ними собственную работу ноды. SCHED_DEADLINE подам не предлагается: ядро допускает его только для задач, которым разрешены все процессоры их домена планирования, а процессоры пода закреплены.

Насколько поздно нода будит задачу реального времени — ресурс API ноды, `latencytests`: cyclictest запускает поток SCHED_FIFO на каждом заданном процессоре, по умолчанию на процессорах без таймерного тика, и тест сообщает по каждому процессору и в целом наименьшую, среднюю и наибольшую задержку, а также 99-й и 99,99-й процентили.

```yaml
apiVersion: node.kuberoot.dev/v1alpha1
kind: LatencyTest
metadata: {name: baseline}
spec: {durationSeconds: 300}
```

Дистрибутиву нужны четыре процессора или больше. Ядро для него собирается отдельно от ядра остальных дистрибутивов (`distros/rt/kernel.config`); на amd64 раскладка процессоров входит в собственную командную строку ядра.

## Дистрибутив iot

`iot` — шлюз: он читает устройства в цеху и передаёт дальше то, что они сообщают. Как и маршрутизатор, это Kubernetes без контейнеров. Нода хранит свои устройства и маршруты в собственном API-сервере как ресурсы `devices.kuberoot.dev`, а работу делает `kuberoot-devices`, процесс самой ноды. Ни kubelet, ни среды контейнеров, ни kube-proxy, ни планировщика нет. Нода — это ядро, init, API-сервер и один контроллер.

```yaml
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Device
metadata: {name: press-7}
spec:
  protocol: modbus-tcp
  address: 10.0.5.20:502
  every: 1s
  points:
  - {name: temperature, kind: holding, register: 0, type: int16, scale: "0.1", unit: "C"}
  - {name: running, kind: coil, register: 0}
---
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Route
metadata: {name: overheat}
spec:
  device: press-7
  points: [temperature]
  when: "running && temperature > 80"
  to:
    mqtt: {broker: "tcp://broker.plant:1883", topic: factory/press-7/alarm, qos: 1}
```

Device опрашивается по своему расписанию через одно соединение Modbus TCP. Его статус показывает, отвечает ли устройство, и его значения (`kubectl get devices` выводит их списком). Route отправляет в MQTT-топик каждое чтение, а с `when` — выражением CEL над точками устройства — только в момент, когда выражение становится истинным. Маршрут, у которого при изменении остались прежние устройство и условие, помнит, выполнялось ли условие, поэтому изменение не отправляет ту же тревогу дважды.

Изменения проходят испытание под Safeguard (`kind: Safeguard` с именем `default`). Если после изменения замолчало устройство, которое отвечало, или стал недоступен брокер, который принимал сообщения, изменение откатывается сразу: нода возвращается к последней подтверждённой конфигурации, сохраняет её между перезагрузками и помечает ресурсы, которые не выполняет, как `RolledBack` с причиной. Изменение, которое прошло испытание исправным, становится окончательным само, а при `autoConfirm: false` — только через `spec.confirm`.

Почему без подов: шлюз делает одну работу рядом с устройствами, часто на небольшом железе и там, где рядом никого нет. Здесь код протоколов, конфигурация и операционная система — один образ, который обновляется через A/B-слоты целиком и целиком откатывается. Конфигурация типизирована и проверяется при записи. Она проходит через RBAC и аудит, её можно ревьюить как код, и она откатывается сама, если отрезала устройство. На тестовой ноде вся система заняла около 630 МиБ, большую часть — API-сервер; `kuberoot-devices` — 35 МиБ.

## Дистрибутив observability

`observability` — кластер мониторинга, который стоит снаружи того, за чем следит, и поэтому видит и сообщает о проблеме, даже когда наблюдаемое лежит. Это edge с подами и пакетами: VictoriaMetrics, VictoriaLogs, алерты и дашборды Perses приходят из метапакета `kuberoot-observability`. То, за чем он следит помимо софта, описывается ресурсами `devices.kuberoot.dev`. Их читает `kuberoot-devices` на control plane, и никаких экспортеров запускать не нужно:

```yaml
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Device
metadata: {name: bmc-a3-01}
spec:
  protocol: redfish
  address: https://10.0.9.11
  every: 30s
  tls: {insecureSkipVerify: true}
  credentials: {name: bmc-rack-a3}     # Secret в kube-system: username, password
---
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Device
metadata: {name: pdu-a3}
spec:
  protocol: snmp
  address: 10.0.9.20
  snmp: {version: "3"}
  credentials: {name: snmp-noc}        # username, authProtocol, authPassword, privProtocol, privPassword
  points:
  - {name: load, oid: 1.3.6.1.4.1.318.1.1.12.2.3.1.1.2.1, scale: "0.1", unit: A}
---
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Device
metadata: {name: portal}
spec: {protocol: http, address: "https://portal.example.org/healthz", every: 15s}
---
apiVersion: devices.kuberoot.dev/v1alpha1
kind: Heartbeat
metadata: {name: outside}
spec:
  url: https://hc.example.org/ping/0b6f...
  every: 1m
  query:
    url: http://vmsingle-victoria-metrics.monitoring.svc:8428
    expr: max(time() - timestamp(kuberoot_device_up)) < 120
```

BMC сам сообщает, что у него есть. Демон обходит его системы, шасси и контроллеры через Redfish и называет значения по ним: `temperature_cpu1_temp_celsius`, `fan_..._rpm`, `power_..._watts`, `psu_..._health` (0 — норма, 1 — предупреждение, 2 — авария), а также число записей в журналах. SNMP-устройство читает OID, указанные в его точках, по версии 2c или 3. Проба (`http`, `tcp`, `icmp`) измеряет `up`, `latency_seconds` и HTTP-`status`. Недоступный сервис — тоже показание. Каждое значение — метрика Prometheus `kuberoot_device_value{device,point}` вместе с `kuberoot_device_up` на порту 9790 ноды. Её отдаёт Service `kube-system/kuberoot-devices`, который демон держит на адресе ноды. Метапакет собирает эти метрики и показывает их в дашборде Perses (дашборды и источники данных — ресурсы `PersesDashboard` и `PersesGlobalDatasource`). Он поднимает алерты на устройства, которые перестали отвечать, и на здоровье, ставшее аварийным. Изменения проходят испытание под Safeguard, как в iot: изменение, сломавшее работавшую цель, откатывается.

Heartbeat — это dead man's switch. Каждый период он обращается к URL за пределами кластера, но только пока его запрос находит то, что ищет. Поэтому кластер, переставший собирать данные, замолкает так же, как упавший, и внешний сервис поднимает тревогу. Алерт метапакета `Watchdog`, который горит всегда, решает ту же задачу для цепочки алертов, если Alertmanager направляет его в такой сервис.

## Дистрибутив workstation

`workstation` держит рабочие столы людей в кластере: VDI без Citrix и vCenter. Это дистрибутив hypervisor с рабочими местами поверх. Рабочее место — виртуальная машина с рабочим столом и реплицированным диском. Она продолжает работать, когда ноутбук, с которого её открыли, закрывают, и переезжает между нодами, как любая машина: на тестовом кластере сеанс рабочего стола, открытый через шлюз, продолжал отвечать, самый медленный кадр — меньше 10 мс, пока рабочий стол живьём переезжал на другую ноду.

```yaml
apiVersion: workstation.kuberoot.dev/v1alpha1
kind: Workspace
metadata: {name: anna}
spec:
  owner: anna
  cpus: 2
  memory: 2Gi
  disk: 6Gi
```

`kuberoot-wsctl` на control plane делает из рабочего места VirtualMachine из облачного образа (Ubuntu 24.04, если `spec.image` не называет другой). cloud-init образа ставит рабочий стол при первой загрузке: учётную запись владельца, Xfce, VNC-сервер, который держит сеанс между подключениями, и xrdp для RDP-клиентов. Пока рабочий стол не отвечает, рабочее место в фазе `Provisioning`, потом — `Ready`. В его статусе — адрес, по которому оно открывается в браузере (`status.url`), и адрес для RDP-клиента (`status.rdp`). Secret, который называет `status.credentials`, хранит токен рабочего места и пароль владельца.

Шлюз — часть `kuberoot-wsctl`, процесса ноды control plane, порт 6080. Браузеру, который пришёл с токеном рабочего места, он отдаёт noVNC и проводит WebSocket noVNC до VNC-сервера рабочего стола, а тот спрашивает пароль владельца. Ещё у каждого рабочего места свой RDP-порт на ноде, проброшенный до xrdp. Графической консоли у cloud-hypervisor нет, поэтому рабочий стол отдаёт сам гость, а кластер даёт путь к нему. Пока шлюз работает по обычному HTTP: ставьте перед ним TLS; следующий шаг — единый вход (OIDC) вместо токенов.

Данные cloud-init машина получает от шлюза машин, а не с диска-семени: у VirtualMachine может быть `userData`, прямо в спецификации или в Secret, шлюз отдаёт их только по адресу этой машины, а машина находит их по своему серийному номеру DMI (`ds=nocloud;s=…`). Этим может пользоваться любая VirtualMachine дистрибутива hypervisor.

Рабочий стол Windows встаёт так же: образ Windows с включённым RDP и своей автоматической установкой вместо cloud-init, а RemoteApp открывает отдельные приложения, а не весь рабочий стол. Для этого нужны лицензии, поэтому в демонстрации Linux.

## Несколько control plane

Один control plane хранит состояние кластера в kine на SQLite: без соседей и без настройки. Кластер, который должен пережить потерю control plane, хранит его в etcd; это выбирается при создании кластера: первую ноду загружают с `kuberoot.datastore=etcd` (на загрузочном носителе — `mkimage -args kuberoot.datastore=etcd`). Выбор остаётся за кластером: кластер, созданный на kine, остаётся на kine.

На etcd первый control plane запускает участника хранилища со своим удостоверяющим центром для соседей и клиентов хранилища — отдельно от центра кластера, который подписывает и сертификаты kubelet. Остальные control plane присоединяются через API ноды, как рабочие ноды, — с ролью и адресом, по которому их находят другие участники:

```yaml
apiVersion: node.kuberoot.dev/v1alpha1
kind: JoinTicket
metadata: {name: cp-2}
spec:
  nodeName: kuberoot-dcaf7a
  role: ControlPlane
  address: 10.0.0.12
```

Билет добавляет ноду в хранилище как learner — голос она получает, когда догонит остальных, — и передаёт ей то, что у всех control plane одинаково: удостоверяющие центры кластера, ключ сервисных аккаунтов и ключ, которым шифруются Secret. Применённый как `Membership` ноды, он запускает на ней свои API-сервер, controller manager и scheduler; контроллеры и пакетный менеджер выбирают лидера среди control plane. Три control plane держат кластер при потере одного, пять — при потере двух.

Рабочие ноды кластера из нескольких control plane ходят в API через балансировщик на самой ноде, в API ноды: он отдаёт каждое соединение тому control plane, который отвечает, и следит за control plane по сервису `kubernetes` самого кластера — какие пришли, какие ушли. Ни виртуального адреса, ни балансировщика вне кластера не нужно, поэтому это работает в любой сети.

`etcdmembers` на control plane показывает участников хранилища; удаление участника убирает его из хранилища — так заменяют потерянный control plane: удалить его участника, потом присоединить новую ноду. Control plane, который уходит из кластера (удаление его `Membership`), сначала сам выходит из хранилища. Ставьте control plane на диск до присоединения: установка переносит хранилище одиночного участника, но не одного из нескольких. Перевод существующего кластера с kine на etcd не автоматический: создайте новый кластер на etcd и перенесите нагрузки (Velero или пакеты с их данными).

## Флот edge-нод

В магазинах, на вышках и заводах стоит по своей ноде — кластеру из одной ноды, часто за NAT и на плохой связи. Флот управляет ими из одного центрального кластера, центра, без входящих портов на нодах: каждая нода сама звонит в центр и держит соединение открытым, а центр ходит в API ноды через него — HTTP/2 внутри соединения, которое открыла нода. Центр — это `kuberoot-fleet`; его запускает control plane edge, загруженный с `kuberoot.fleet-center` (или `kuberoot.fleet-center=<host:port>,...`, чтобы назвать адрес, по которому ноды находят центр через NAT). Свои ресурсы он ставит сам, поэтому его можно запустить в любом кластере с kubeconfig. Сторона ноды — часть API ноды: ничего не нужно ставить, контейнеры не нужны.

Нода входит во флот по одноразовому токену. Его выдаёт создание `FleetNode` в центре: Secret в `kube-system` хранит готовый `FleetEnrollment`, который применяет к ноде оператор на месте или загрузочный носитель:

```yaml
apiVersion: fleet.kuberoot.dev/v1alpha1
kind: FleetNode
metadata: {name: shop-12, labels: {region: north, site: shop-12}}
---
# из Secret kube-system/fleet-enroll-shop-12, применяется к самой ноде
apiVersion: node.kuberoot.dev/v1alpha1
kind: FleetEnrollment
metadata: {name: center}
spec:
  name: shop-12
  servers: [fleet.example.org:7443]
  caHash: sha256:4769fc58...   # удостоверяющий центр центра, закреплён
  token: ...                   # работает один раз
```

Обе стороны закреплены. Нода говорит только с центром, чей удостоверяющий центр даёт хеш `caHash`. Когда токен потрачен, центр закрепляет собственный удостоверяющий центр ноды — тот, что есть у каждой ноды kuberoot для её API, — и дальше открывает соединение ноды только по клиентскому сертификату, который этот центр выдал на имя ноды. Удаление FleetNode или FleetEnrollment ноды прекращает её участие.

`FleetNode` — это инвентарь: подключена ли нода и с какого времени, какой выпуск и слот она загрузила и в каком они состоянии, её службы, здоровье и когда её видели в последний раз, с метками площадки, региона или железа (`fleet.kuberoot.dev/arch` и `/distro` центр ставит сам по тому, что сообщает нода). `spec.release` — выпуск, на котором нода должна работать: пока нода подключена, центр ставит его через `Upgrade` самой ноды и читает результат по её загрузочным записям. Поэтому нода, у которой кончились попытки загрузки и которая вернулась на прежний слот, — `RolledBack`; это видно и после любой перезагрузки или перезапуска центра, и этот выпуск ей больше не дают.

`FleetRollout` раздаёт выпуск нодам волнами:

```yaml
apiVersion: fleet.kuberoot.dev/v1alpha1
kind: FleetRollout
metadata: {name: release-0.9.0}
spec:
  release:
    version: 0.9.0
    url: https://releases.example.org/kuberoot-0.9.0-amd64.tar
    sha256: f5fa3786...
  selector: {matchLabels: {region: north}}
  waves: ["1", "10%", "100%"]   # у скольких нод выпуск после каждой волны
  maxFailures: 0
  offline: Wait                 # или Skip
  soak: 30m                     # необязательно: сколько волна работает до следующей
```

Ноды фиксируются при старте раскатки и берутся по порядку имён. Волна начинается, когда все ноды предыдущих волн обновились (и отстоялись, если задан `soak`). Нода, которая откатила выпуск или не смогла его поставить, — сбой; больше `maxFailures` сбоев останавливают раскатку: ноды, до которых она не дошла, остаются на своём, а остановленная раскатка продолжается, только когда меняется её spec. `paused: true` придерживает следующую волну. Нода, которая не на связи, когда приходит её волна, либо держит волну (`Wait`), либо остаётся позади (`Skip`); в обоих случаях выпуск ей назначен, и она берёт его, когда снова выходит на связь. Без центра нода продолжает работать; центр действует, только когда слышит ноду. Нода принадлежит самой новой раскатке, которая дала ей выпуск.

Ещё центр отдаёт своим пользователям API подключённой ноды по адресу `https://<center>:7443/nodes/<name>/`: `kubectl` с клиентским сертификатом центра и его удостоверяющим центром (ConfigMap `kube-system/kuberoot-fleet-ca`, имя сервера `kuberoot-fleet`) видит `nodeservices`, `bootentries` и остальное у той ноды, на которую RBAC центра разрешает `get` для `fleetnodes/proxy`.

Чего пока нет: центр — один процесс, без отказоустойчивости; центр действует на ноде как её администратор, так что кто владеет центром, владеет флотом; токены сами не истекают (чтобы отозвать, удалите FleetNode); ноды, добавленные после старта раскатки, в неё не входят; через центр доступен только API ноды, не её собственный кластер (поды, `devices`); и проверено это на четырёх нодах, а не на тысячах.

| Ресурс | Что делает |
|---|---|
| `osconfigs` | настройки операционной системы ноды |
| `nodeservices` | службы, которые запускает kinit, их состояние и логи |
| `disks` | блочные устройства |
| `installations` | записывает систему на диск, с загрузочного носителя |
| `bootentries` | два корневых слота и какой из них загружается |
| `upgrades` | записывает подписанный выпуск в неактивный слот |
| `memberships`, `jointickets` | присоединяют ноды к кластеру — рабочими или control plane |

## Установка и обновление

Нода загружается с носителя (`mkimage` пишет образ диска с ядром, initramfs и корневой системой). В живой системе `Installation` размечает диск: EFI-раздел с systemd-boot, два корневых слота и раздел состояния. Вместе с системой на диск переезжают идентичность ноды, её членство в кластере и, на control plane, снимок хранилища кластера.

`Upgrade` скачивает подписанный выпуск, пишет его в неактивный слот и загружает на испытательный срок: если за пять минут все службы не работают без перезапусков и нода не стала Ready, она перезагружается, а когда попытки кончаются — снова загружает прежний слот.

## Резервные копии control plane

Control plane держит своё состояние в одном месте: хранилище кластера, его удостоверяющие центры и идентичность ноды. API ноды архивирует его каждый час и по запросу (`kubectl create statebackup`), хранит последние двенадцать на ноде и, если так сказано в Secret `kube-system/kuberoot-state-backup`, выгружает в S3-совместимое хранилище:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: kuberoot-state-backup
  namespace: kube-system
stringData:
  interval: 1h
  keep: "12"
  encryptionRecipient: age1...        # архивы шифруются на этот ключ age
  s3Endpoint: https://s3.example.org
  s3Bucket: backups
  s3AccessKey: ...
  s3SecretKey: ...
```

В архивах ключи кластера и все его Secret, поэтому с ноды они уходят только зашифрованными (`age-keygen` делает пару ключей; секретный остаётся у вас). Чтобы вернуть потерянный control plane на новом железе, загрузите новую машину с носителя и установите её из копии:

```yaml
apiVersion: node.kuberoot.dev/v1alpha1
kind: Installation
metadata:
  name: restore
spec:
  disk: vda
  reboot: true
  restore:
    url: https://...      # подписанная ссылка на архив
    sha256: ...           # как его показывает StateBackup
    identity: AGE-SECRET-KEY-1...
```

Нода возвращается той же нодой — с тем же именем, сертификатами и кластером. На etcd архив содержит снимок хранилища, и восстановленная нода запускает хранилище из него как единственный участник; остальные control plane присоединяются к ней заново.

## Сборка

Сборка идёт в контейнере с инструментами, а не на рабочей машине: в `scripts/` лежат шаги (ядро, DRBD, программы, корневая система, initramfs, выпуск). `hack/hetzner.sh` управляет подом-сборщиком в кластере Kubernetes и запускает их там; в `hack/hetzner/` — сборщик, реестр и описания ВМ, на которых автор проверяет ноды.

```sh
hack/hetzner.sh build amd64      # ядро, если его нет, программы, корневая система, initramfs
hack/hetzner.sh bundle amd64     # подписанный выпуск
hack/hetzner.sh media amd64      # загрузочный носитель
hack/hetzner.sh test             # go test ./...
```
