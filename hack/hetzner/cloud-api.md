# Installed stage2 API transition acceptance

Use only the separately created `cloud-stage2-1` lab from `cloud-api-node.yaml`. Accepted stage0/stage1 guests, disks, sources and images are outside this procedure. The lab initially boots the immutable accepted stage1 media and stores/serves cluster-scoped VM alpha1. It must be installed on its newly created blank system disk before acceptance. Installation erases that target disk; execute it only with authorization for the verified new disk. The first attempt was rejected by automatic approval review and was not executed. Do not infer authorization from elapsed time or use an alternate write path.

The node identity observed at preparation was `kuberoot-546b7c`, UID `0de7271189dbb8728b94b390da9681f4`, IP `10.244.7.112`. The media was `vda` with `BootMedia` role and `KUBEROOT-MEDIA` partition. The blank 20 GiB system disk was `vdb`, UID `0de7271189dbb8728b94b390da9681f4-disk-vdb`, with no partitions. Re-read and verify these facts before any installation; this historical record alone is not a target check. After successful installation, remove the media only from this new VM's template, retain its MAC and boot solely from its system disk.

The subsequent transition image must be built with `KUBEROOT_VM_API_TRANSITION=1`, signed by the lab's existing trusted release key and upgraded through the supported A/B workflow. That host upgrade and its reboot happen **before** the preservation baseline. Do not use a binary from `/tmp`, kill an unmanaged process or mutate accepted stage1 images. Confirm installed BootEntry, etcd, NodeReady, packages and ordinary Pod readiness. Keep upstream `main` plus the separate signed cloud package catalog; do not replace the union with an incomplete repository.

The transition controller must acknowledge `v1alpha1` with an authenticated principal and current process incarnation before proceeding. Confirm transition add-ons preserve the existing legacy CRD, finish other add-ons/packages and leave no permanent CRD scope-conflict loop. Apply `cloud-api-smoke.yaml` once to this legacy lab. Its native guest exposes read-only identity evidence over HTTP from the ordinary observer Pod. The pinned Debian disk and digest are the same verified input as the accepted [stage0 smoke](cloud-smoke.md#image-preflight). Wait for native PID, guest console marker and successful HTTP; `Running` by itself does not prove a booted guest.

Store private kubeconfigs and migration plans in a mode-0700 directory under `/work`; token and key contents must never enter an evidence report. Use explicit kubeconfig/context on every kubectl command. Create a dedicated temporary executor identity in this lab and verify its SelfSubjectReview username differs from all Guard principals. It needs administration and impersonation privileges for this disposable acceptance. Export only its username, not token/groups/extra. Keep the same identity across prepare/cutover/recovery/resume. Test that the ordinary shared controller identity is rejected before creating a maintenance gate.

After the transition rollout and guest readiness, capture:

- VM old API UID, full original object and spec, MAC/address, replica placement and disk identity binding.
- Node Machine PID and `startedAt`, node OS `bootTime`, vmctl/wsctl supervised PID plus process start ticks/boot ID, actual controller principal.
- Native Volume spec/status, all backends and every dependent; private bootstrap Secrets belong only in the protected backup.
- Guest `boot_id`, monotonically increasing `uptime_seconds`, `root_uuid`, `marker_sha256`, `cloud_init_instance_id` and `system_serial` from the observer Pod.

Use the explicit helper sequence in [the API runbook](../../docs/vm-api.md#operator-sequence) with map `{"api-preserve":"cloud-api"}` and the actual node's direct verified-TLS API endpoint. The endpoint must be the local API listener, not a proxy or load balancer. Save the immutable plan SHA256 and durable checkpoint before destructive CRD replacement. Confirm the real non-executor dry-run receives the exact session policy denial. Leave the gate and fences intact on any error; recover using the same plan and checkpoint.

After verified import, restart only vmctl/wsctl with `NodeService.spec.restartedAt`, including every standby participant. Require fresh alpha2 acknowledgements before resume. The same installed transition executable chooses the alpha2 branch. Do not reboot the host or native guest during this interval. Record the gateway/seed interruption separately; temporary HTTP failure does not by itself prove a guest restart, and an unchanged HTTP response does not prove the controller barrier.

After resume, prove old alpha1 scope is gone, alpha2 `cloud-api/api-preserve` has a new API UID with the old `status.backendID` and `status.instanceID`, and no unexpected native backend exists. Compare native PID/startedAt, host bootTime, guest boot ID, filesystem UUID, persistent marker hash, cloud-init identity, DMI serial, MAC/IP and replica placement with the baseline. Require greater guest uptime and resumed reconciliation/HTTP. API-derived Volume UID is name-based; use actual guest UUID/marker in addition to the API binding. Confirm helper retry after completion is idempotent and its own gate/fences/probe RBAC are removed with UID checks.

Finally test namespace and bootstrap Secret isolation with separate temporary alpha2 fixtures, and verify a later image/add-on reconciliation cannot reinstall legacy scope. Delete only explicitly owned temporary fixtures after recording results; retain this acceptance guest and its evidence. This document is a prepared procedure, not evidence that installed guest-preserving cutover or Talos bootstrap has passed.
