# Хранилище в модели ресурсов Kubernetes

Статус: лаборатория. Ядро построено и реплицируется; слой ресурсов и
протокольные слои — пока проекты. Ничто здесь не предназначено для
продакшена, и ничто не использует его по умолчанию.

## Зачем

Кластер Kubernetes хранит состояние в etcd: реплицируемом упорядоченном
хранилище «ключ — значение», которое API-сервер читает и пишет через API etcd
v3. kuberoot запускает etcd на отказоустойчивых control plane и kine на
одиночных. Работает и то и другое. Лаборатория задаёт другой вопрос: каким
было бы хранилище, чья родная модель — модель самого API (типизированные
объекты с версиями, лента изменений, схемы и правила доступа), чтобы одно и то
же хранилище обслуживало и control plane, и, через API Kubernetes, приложения,
которые держат свои данные как ресурсы?

API Kubernetes — это уже почти документная база данных: объекты с apiVersion
и kind, метаданными и spec, resourceVersion для оптимистичной конкуренции,
watch как лента изменений, схемы с валидацией (CRD, OpenAPI, CEL), метки,
RBAC, ссылки на владельцев и сборка мусора, server-side apply. Для данных
приложений ему не хватает масштаба на тип (API-сервер читает и кеширует тип
целиком), запросов шире селекторов по меткам и полям и вторичных индексов.

## Границы

Хранилище строится слоями над одним ядром, как слои записей и документов
строят над FoundationDB:

1. **Ядро:** упорядоченное транзакционное хранилище «ключ — значение» с
   многоверсионностью, реплицируемое Raft. Watch — это чтение его журнала
   изменений. Ядро говорит на API etcd v3, на той его части, которой
   пользуется kube-apiserver, поэтому API-сервер работает на нём без
   изменений.
2. **Слой ресурсов:** объекты в том виде, в каком их пишет API-сервер, со
   вторичными индексами, объявленными для типа (путь к полю, которое
   извлекается при записи объекта и хранится в той же транзакции), и запросы
   по ним.
3. **Протокольные слои (демонстрации):** документный протокол (MongoDB wire),
   SQL (PostgreSQL wire, подмножество), кеш (RESP с TTL и pub/sub поверх
   watch). Каждый — отображение на ключи ядра, а не отдельное хранилище.

Вне границ: SQL-оптимизатор, задержки кеша в памяти при репликации каждой
записи, скорость выше, чем у специализированного хранилища каждой модели.
Единая модель даёт другое: одни правила доступа, одну ленту изменений, одну
систему схем и одну резервную копию на всё.

## Что kube-apiserver нужно от хранилища

kube-apiserver пользуется небольшой частью etcd v3:

| RPC | Зачем |
|---|---|
| `KV.Range` | прочитать один ключ; прочитать префикс с лимитом и продолжением; посчитать ключи префикса; прочитать на ревизии |
| `KV.Txn` | создать, если нет (`create_revision == 0`), обновить или удалить, если не изменилось (`mod_revision == n`), и вернуть текущее значение, если сравнение не прошло |
| `KV.Compact` | отбросить историю старше ревизии (раз в пять минут) |
| `Watch.Watch` | изменения префикса с ревизии, с предыдущим значением; уведомления о прогрессе |
| `Lease.*` | события и другие объекты с временем жизни |
| `Maintenance.Status` | здоровье и размер базы |

Ключи — `/registry/<resource>/<namespace>/<name>`; значения — объекты в
protobuf или JSON, для некоторых типов зашифрованные. Каждая запись получает
новую ревизию, общую для кластера, а `resourceVersion` объекта — это ревизия
его последней записи.

## Устройство ядра

### Модель данных

Ядро хранит для каждого ключа его версии: `(ключ, ревизия) -> {значение,
ревизия создания, lease, отметка удаления}`, упорядоченные по ключу, затем по
ревизии. Текущая ревизия — один счётчик, который продвигает каждая
зафиксированная запись. Чтение на ревизии `r` видит для каждого ключа его
самую новую версию не позже `r`. Компакция на `r` удаляет для каждого ключа
все версии раньше самой новой версии не позже `r`, а также отметки удаления
старше `r`.

Журнал изменений — последовательность зафиксированных записей по ревизиям.
Watch с ревизии `r` проигрывает журнал после `r` для своего префикса, затем
следует за новыми записями. Watch со сжатой ревизии получает ошибку, как в
etcd.

### Движок хранения

Версии на диске держит встраиваемый упорядоченный движок «ключ — значение»:
bbolt (как в etcd) или Pebble (как в CockroachDB). Хранилище использует
bbolt: это движок etcd, хорошо изученный, и это один файл, который снимок
копирует целиком. Ключи кодируют `(ключ, ревизия)`, так что чтение
диапазона по префиксу отдаёт версии по порядку; отдельный индекс от ключа к
его последней ревизии делает чтение текущего значения точечным.

### Репликация

Записи идут через Raft: запись — это элемент журнала; зафиксированный, он
применяется к движку в порядке журнала на каждом участнике, и ревизию
продвигает само состояние, поэтому она одна и та же у всех участников.
Чтения, которые должны быть линеаризуемыми (кворумные чтения API-сервера),
ждут read index, как в etcd.

Сравнивались две библиотеки Raft:

- **`go.etcd.io/raft` из etcd:** библиотека, на которой работает сам etcd,
  её же используют CockroachDB и другие; это только машина состояний (без
  транспорта и хранения), поэтому хранение журнала и транспорт хранилище
  пишет само. В ней есть learner'ы, joint consensus для смены состава,
  read index, pre-vote и check-quorum. Её семантика в точности та же, что у
  etcd, поэтому модель участников, которой kuberoot уже пользуется (сначала
  learner, потом повышение), переносится как есть.
- **`hashicorp/raft`:** готовый Raft с транспортом и хранением журнала
  (BoltDB), его используют Consul, Nomad и Vault. С ним проще начать, но его
  learner'ы («non-voters») и смена состава устроены иначе, чем в etcd, а
  read index нет: линеаризуемые чтения идут через журнал или через аренду
  лидера.

Выбран `go.etcd.io/raft`: API-сервер испытан именно на семантике etcd, и
хранилище должно отказывать так же, как отказывает etcd.

### Транзакции

Транзакции API-сервера сравнивают `mod_revision` одного ключа (или
`create_revision == 0`), затем записывают или удаляют этот ключ, а при
неудаче возвращают текущее значение. Ядро реализует общие транзакции etcd
(сравнение набора ключей, затем набор операций), которые применяются как один
элемент журнала Raft и проверяются по состоянию на момент применения. В
слое ресурсов транзакция заодно обновляет индексные записи объекта, в том же
элементе журнала.

## Слой ресурсов

Индекс объявляется для типа ресурса: префикс ключей типа и путь к полю в
хранимом объекте, например `spec.nodeName` подов или метка. Когда объект
этого типа записывается, шаг применения декодирует его (для custom resources
API-сервер пишет JSON; для встроенных типов — protobuf, который слой
декодирует по схеме типов), извлекает поле и пишет
`index/<тип>/<поле>/<значение>/<ключ>` в той же транзакции. Запрос читает
диапазон индекса для значения и забирает объекты на одной ревизии.

Secrets и другие шифруемые типы для хранилища непрозрачны: API-сервер
шифрует их до того, как их увидит хранилище, и никакой индекс не заглянет
внутрь.

Этим слоем пользовались бы приложения: перечислить поды ноды, не читая все
поды, или найти документы по полю — через агрегированный API рядом с API
кластера, с аутентификацией и RBAC API-сервера перед ним.

## Протокольные слои

Каждый протокол отображается на ключи ядра под своим префиксом и пользуется
транзакциями и watch ядра:

- **Документы:** коллекция — это префикс; документ — ключ со значением в
  JSON; `_id` и объявленные поля — индексы, как выше. Протокол — MongoDB
  wire (так FerretDB работает поверх PostgreSQL).
- **SQL:** таблица — префикс, строка — ключ, первичный и вторичные индексы —
  как выше; подмножество SQL без оптимизатора по стоимости.
- **Кеш:** ключи с TTL как lease; pub/sub как watch. Записи всё равно идут
  через Raft; для ключей, которые могут потерять последние записи,
  асинхронный режим подтверждает запись до репликации.

## Ядро как оно построено

`cmd/kuberoot-store` (`pkg/resourcestore`) — участник хранилища: сервисы KV
(включая `RangeStream`), Watch, Lease, Cluster и Maintenance API etcd v3,
реплицируемые `go.etcd.io/raft` v3.7. Он принимает флаги etcd (`--name`,
`--data-dir`, `--initial-cluster`, `--initial-cluster-state`, клиентские и
пировые адреса и сертификаты, `--snapshot-count`), поэтому работает там же,
где работает участник etcd.

### Репликация

Каждая запись (`Put`, `DeleteRange`, `Txn` с записью, `Compact`, выдача и
отзыв lease) — это запрос в одном элементе журнала. Каждый участник
применяет зафиксированные элементы в порядке журнала к своему состоянию,
файлу bbolt с моделью версий, описанной выше, одной записью файла на пачку
элементов; ревизия — собственный счётчик состояния, поэтому ревизии у всех
участников одинаковые. Follower пересылает свои предложения лидеру, как это
делает Raft, и отвечает, только когда его собственное состояние применило
элемент.

Когда лидер меняется, участник ещё раз предлагает записи, которые всё ещё
ждут ответа: элемент, пересланный лидеру, который умер, мог пропасть вместе
с ним, а мог и зафиксироваться. Состояние какое-то время помнит, какие
запросы оно применило (по предложившему участнику и номеру запроса), поэтому
копия, зафиксированная второй, ничего не делает. etcd так не делает: запись,
попавшая на смену лидера, там завершается ошибкой «request timed out» или
«leader changed», и API-сервер возвращает эту ошибку клиенту.

Чтения линеаризуемы, если клиент не попросил сериализуемое чтение: участник
спрашивает у лидера read index (один запрос на все чтения, ждущие в этот
момент) и читает, когда применил журнал до этого индекса. Learner'ы тоже
обслуживают чтения и записи — etcd им это запрещает.

Журнал Raft, его hard state и метаданные последнего снимка лежат в другом
файле bbolt, который синхронизируется на каждом раунде Raft. Файл состояния
не синхронизируется при каждом применении: перед тем как снимок позволит
отбросить журнал до него, состояние синхронизируется, поэтому участник после
падения заново применяет элементы после последнего снимка. Раунды дольше
половины таймаута выборов пишутся в журнал: они задерживают heartbeat'ы, и
медленный диск стоит лидерства так же, как в etcd.

### Снимки и сжатие журнала

Каждые `--snapshot-count` применённых элементов (по умолчанию 10 000)
участник записывает снимок на своём применённом индексе и отбрасывает
журнал до него, оставляя `--snapshot-catchup-entries` (5 000) для
участников, немного отставших. Снимок записывается и при каждой смене
состава, без отбрасывания журнала: Raft отправляет участнику самый новый
снимок и отказывается принять снимок, в составе которого нет его самого, —
а именно такой получал learner, добавленный после последнего снимка.

Участник, отставший настолько, что журнала ему не хватает, получает
сообщение снимка и в том же запросе копию файла состояния лидера на момент
отправки. Это состояние содержит по меньшей мере то, что содержит снимок;
участник берёт его вместо своего и пропускает элементы, которые в нём уже
есть. Его watch'и завершаются, и их клиенты подписываются заново.

### Lease

Lease и привязанные к ним ключи — реплицируемое состояние, в отличие от
прототипа. Их часы — нет: как в etcd, часы держит лидер, keep-alive на
follower'е идут к лидеру, а участник, ставший лидером, даёт каждой lease
полное время жизни заново, поэтому смена лидера никогда не истекает lease.
Истёкшую lease лидер отзывает через журнал; отзыв удаляет её ключи одной
ревизией на всех участниках.

### Состав

Cluster API — как в etcd: `MemberAdd` (learner'ом или голосующим),
`MemberPromote`, `MemberRemove`, `MemberUpdate`, `MemberList`. Learner
повышается, когда его журнал отстаёт от журнала лидера не больше чем на
десятую часть, как проверяет etcd; знает это только лидер, поэтому другой
участник спрашивает лидера по пировому соединению. Новый участник,
запущенный с `--initial-cluster-state existing`, находит свой ID по своему
пировому адресу в списке участников у остальных. ID участников нового
хранилища вычисляются из пировых адресов и токена кластера, поэтому все
участники получают одни и те же. Удалённый участник узнаёт об этом из
журнала или из отказа соседей и останавливается; его ID вернуться не может.

Участники общаются по HTTP или HTTPS со взаимными сертификатами: сообщения
Raft пачками, по одной упорядоченной очереди на соседа, снимки отдельно.

`Maintenance.Snapshot` отдаёт потоком копию файла состояния, а
`kuberoot-store snapshot restore FILE --data-dir DIR` делает из неё новое
хранилище, с флагами etcdutl `--name`, `--initial-cluster` и
`--initial-advertise-peer-urls` (ключи, ревизии и lease; без состава,
журнала и запомненных запросов) — как `etcdutl snapshot restore` для etcd.
Новый журнал начинается со снимка Raft восстановленного состояния, поэтому
участник, который присоединится позже, получит состояние, а не пустой
журнал. Формат свой: etcd и etcdutl его не прочтут.

### Что нужно API-серверу сверх написанного в API etcd

- **Новое хранилище начинается с ревизии 1, а не 0.** Ревизию 0 API-сервер
  читает как «ревизии нет» и отказывается стартовать.
- **`RangeStream`.** API-сервер 1.37 читает списки через потоковый range из
  etcd 3.7, когда хранилище сообщает версию 3.7, и переходит на постраничные
  range, только если вызов не реализован.
- **Уведомления о прогрессе.** Уведомление о прогрессе в потоке watch
  утверждает, что все события до его ревизии отправлены. Хранилище отдаёт
  каждому watch каждую применённую пачку, есть в ней события для него или
  нет, и на запрос прогресса отвечает наименьшей ревизией, до которой
  отправили события его watch'и.
- **Keep-alive.** Клиент etcd в API-сервере пингует простаивающие
  соединения; хранилище разрешает пинги раз в 5 секунд, как etcd, вместо
  того чтобы закрывать соединение с «too many pings».

### Вместо etcd

Образ, собранный с `KUBEROOT_STORE_LAB=1`, несёт `/usr/bin/kuberoot-store`;
остальные — нет. Загруженная с `kuberoot.datastore=kuberoot-store` нода,
которая создаёт кластер, запускает хранилище там, где запустила бы etcd: те
же сертификаты, порты и каталог данных, тот же `JoinTicket` для других
control plane (learner, повышаемый, когда догонит), `etcdmembers`, чтобы
смотреть и удалять участников, тот же перенос хранилища на диск при
установке, и резервные копии, восстанавливаемые собственным restore
хранилища. Нода, которую просят о лабораторном хранилище в образе без него,
создаёт кластер на kine. Выбор остаётся за кластером, как с etcd.

## Замеры

### Модульные тесты

`go test ./pkg/resourcestore/` гоняет участников в одном процессе через
собственный клиент etcd (`clientv3`), с настоящим HTTP между участниками: на
одном участнике — транзакции API-сервера, постраничные списки, компакцию,
watch из прошлого, lease и `RangeStream`; на трёх — запись на follower'е,
сразу читаемую на каждом участнике, потерю лидера и его возвращение из
журнала, learner'а, добавленного после сжатия журнала, который догоняет по
снимку и повышается через follower'а, удалённого участника, который
останавливается и чей ID нельзя удалить ещё раз, перезапуск с сохранением
состояния и ревизий, реплицируемые lease, которые переживают потерю лидера и
истекают при новом, и восстановление из `Maintenance.Snapshot`. Тесты
состояния применяют запросы напрямую: запрос, зафиксированный дважды,
применяется один раз, элементы, которые в состоянии уже есть, пропускаются,
неудавшаяся транзакция ничего не пишет, отозванная lease удаляет свои
ключи. Тесты проходят с детектором гонок.

### kube-apiserver на трёх участниках

В поде builder: три участника на одной машине, у каждого свой каталог данных
на томе builder'а, и kube-apiserver v1.37.1 со всеми тремя в
`--etcd-servers`. Он стартует, создаёт свои объекты и работает. Нагрузка —
раунд запросов к API каждую секунду (создать, прочитать, пропатчить,
перечислить страницами по 50 и удалить ConfigMap, через `kubectl`) и watch
всех ConfigMap всё это время, который должен увидеть каждое изменение.

| Испытание | Запросов | Ошибок | Что произошло |
|---|---|---|---|

Каждый watch увидел каждое изменение, которое должен был: событий ADDED,

Том builder'а делят со сборками, и его fsync время от времени замирает на

посреди испытания; запросы ждали до 5 с, ни один не завершился ошибкой. На
таком диске etcd замирает так же.

### Кластер на хранилище и conformance

Три виртуальные машины (по 2 vCPU и 2,5 ГиБ) загружают образ edge,
собранный с лабораторией, с `kuberoot.datastore=kuberoot-store`, и проходят
тот же путь, что и кластер на etcd:

1. Загрузившись с носителя, каждая нода создаёт собственный кластер на
   лабораторном хранилище: один участник.
2. `Installation` записывает каждую на её диск и переносит хранилище
   снимком (`Maintenance.Snapshot`). Загрузившись с диска, нода
   восстанавливает его (`kuberoot-store snapshot restore`): первая нода
   сохраняет свой кластер, нода в нём создана за 26 минут до того.
3. `JoinTicket` на первой ноде добавляет вторую learner'ом; применённый как
   `Membership` второй ноды, он присоединяет её к хранилищу, она получает
   состояние снимком (на индексе журнала 218; третья — на 304), API ноды повышает её, и запускаются
   её kubelet, controller manager и scheduler. Голосующий участник — через
   16 с после применения membership, нода Ready — через 22 с; третья так
   же, 16 и 23 с. API-серверы всех трёх читают одни и те же объекты (один
   UID `kube-system` через каждый).

Две ошибки проявились только на этом пути и исправлены: восстановленное
хранилище начинало новый журнал с индекса 1, хотя его состояние уже
содержало восстановленные ключи, поэтому присоединившийся участник
проигрывал журнал без них, и его API-сервер видел пустой кластер (теперь
журнал восстановленного хранилища начинается со снимка Raft этого
состояния); и kinit держал клиент проверки готовности, собранный из
собственного admin-сертификата присоединяющейся ноды, поэтому после того,
как нода брала удостоверяющий центр кластера, её kubelet и контроллеры ждали
до перезагрузки (теперь клиент пересобирается после неудачного запроса; эта
ошибка не лабораторного хранилища, она касается и etcd).

Conformance (hydrophone, Kubernetes v1.37.1, один поток) на этом
кластере: **462 из 462** за 1 ч 58 мин.

Первый прогон дал 461. Не прошёл тест, проверяющий, что продолжение
списка истекает, когда его ревизию сжали: он берёт первую страницу и
каждые 20 секунд в течение 10 минут просит следующую, пока API-сервер не
ответит, что продолжение устарело. API-сервер сжимает историю раз в 5
минут до ревизии, запомненной на прошлом раунде, поэтому ревизия
сжимается через 5–10 минут после записи. Хранилище сжимало вовремя:
проба самой старой читаемой ревизии раз в 30 секунд показала сжатие
каждые 5 минут, каждый раз до ревизии, текущей 5 минут назад. В том
прогоне первая страница пришла через 1,5 с после раунда компактора,
поэтому её ревизию сжал только раунд через 10 минут — через несколько
секунд после того, как тест перестал спрашивать. Отдельно тест прошёл за
5,6 минуты, второй полный прогон — тоже. В хранилище ради этого ничего не
меняли; на etcd при таком совпадении тест упал бы так же.

## Не сделано

- Слой ресурсов и протокольные слои: только проекты.
- Из API etcd: вложенные транзакции, `Hash`/`HashKV`, тревоги (`Alarm`
  отвечает, что их нет), дефрагментация, аутентификация пользователями и
  ролями (`Auth`), сортировка и фильтры ревизий в `Range`. API-сервер ничем
  из этого не пользуется.
- Элементы журнала — JSON вместе со значениями: просто читать, больше, чем
  protobuf в etcd.
- Снимок отправляет весь файл состояния одним запросом: ни одна сторона не
  держит его в памяти, но и продолжить прерванную отправку нельзя.
- Файл состояния не синхронизируется при каждом применении. Падение
  процесса ничего не теряет (журнал синхронизирован и проигрывается заново);
  потеря питания до того, как операционная система допишет файл, оставляет
  его восстановление bbolt, а тот может не справиться.

## Открытые вопросы

- Компакция и индексы слоя ресурсов: индексная запись должна сжиматься
  вместе с версией, на которую указывает, иначе запросы на старых ревизиях
  прочтут висячие записи.
- Декодирование встроенных типов для индексов привязывает хранилище к
  protobuf-схемам API и их версиям; индексы только для custom resources
  (JSON) этого избегают.
- Место ли слою ресурсов в хранилище или в агрегированном API-сервере перед
  ним, что оставило бы хранилище простой заменой etcd.
